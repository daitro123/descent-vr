# Research: Joining zones without a loading screen

Researched September 2026 for ticket [04](../issues/04-joining-zones-without-a-loading-screen.md), against three.js **r186** (`node_modules/three`, version 0.186.1). It builds on [`docs/quest-3-browser-performance-budget.md`](../../../docs/quest-3-browser-performance-budget.md) (72 fps, 13.9 ms per frame, about 300 draw calls and 300k triangles per frame counted over both eyes, at most 4 point lights). Those budgets are not re-derived here.

**How the sources were read.** The three.js claims were checked in the r186 source in `node_modules/three`, and the links point at the `r186` tag. The WebXR spec, the WHATWG HTML spec, the W3C `requestIdleCallback` spec, the WICG scheduling spec, the Khronos `KHR_parallel_shader_compile` spec, Chromium's GPU client code, V8's docs, MDN, MDN's browser-compat-data and Vite's docs were read from their GitHub sources. That was necessary because this environment's egress policy blocks `developer.mozilla.org`, `html.spec.whatwg.org`, `developer.chrome.com`, `web.dev`, `threejs.org` and `developers.meta.com`. **Claims from Meta's docs come from search-engine extracts and are medium confidence.** Browser-compat-data marks the Quest browser (`oculus`) as `"mirror"` for every API cited here, which means its support is copied from Chrome for Android and has not been tested on the headset. Those claims are also medium confidence. Numbers labelled **(measured)** come from running Oakvale's build in Node on this machine (Intel Xeon at 2.8 GHz, Node 22). Numbers labelled **(rule of thumb)** are derived here and are not documented limits.

## Bottom line for Oakvale

A seamless seam is feasible with the tools already in the stack. It needs four changes to how a zone is built and shown:

| Knob | Setting | Why (short) |
|---|---|---|
| Where zone geometry is built | **In a module Web Worker**, one 40 m chunk at a time, nearest to the player first. Each chunk is posted back as typed arrays in the transfer list, which is zero-copy. The main thread only wraps the arrays in a `BufferGeometry`. | Any long task on the main thread delays the XR frame callback. Oakvale's build takes about 0.6–0.8 s on desktop **(measured)**. It runs without a DOM already, so it can move to a worker as it is. A worker has its own V8 heap, so its garbage never pauses the render thread. |
| GPU upload | **At most one new chunk upload per frame** (0.2–2.5 MB each today). Stage it for one frame with `frustumCulled = false` and a material that has `visible = false`: its buffers upload without a draw, before it can come into view. Measure the per-frame byte budget on the headset. | three.js uploads a mesh's buffers on the first frame the mesh passes frustum culling, not when it is added. In Chromium the upload is a copy through a shared-memory ring buffer that can block the main thread when it fills. |
| Shaders | **No new shader program may appear at the seam.** Every zone uses the shared materials. The lights live in one world-level rig: 1 hemisphere, 1 directional and a pool of 4 point lights. Keep one `Fog` instance and change its `near`, `far` and `color`. Still call `renderer.compileAsync` on each new zone root, and check that `renderer.info.programs.length` does not change. | The light counts and the fog type are part of three.js's program cache key. Today each `GameMap.root` carries its own sun and hemisphere light. A second zone would change the light counts and recompile every lit material mid-walk. |
| What loads, and when | **Stream by chunk distance, not by zone.** A zone is the unit of authoring: its plan, atmosphere and colliders. A chunk is the unit of loading. Use full detail within about **120 m**, a cheap proxy (coarse ground plus the existing "far" trees) out to the draw distance, and unload one chunk (40 m) beyond each radius. Load a neighbouring zone's *plan* as soon as its zone becomes a neighbour of the current zone. | With a 240 m far plane and a 280 m zone, "load when near the seam" means "load on entering the zone" anyway. Chunk streaming also caps triangles: today Oakvale shows about 24 chunks and 120–150k triangles per eye from the village **(measured estimate)**. That is already at the 300k two-eye rule of thumb. |
| Fog and far plane | **Make fog radial** (`vFogDepth = length(mvPosition.xyz)`), and cull chunks by distance at `fog.far` plus the chunk radius. Otherwise the stream radius must be `far / cos(half-FOV)`, about 420 m at a 110° FOV. | three.js fog and the far plane both use view depth, not distance. Things at the edge of a wide XR view are less fogged than things straight ahead at the same distance. |
| Unloading | `scene.remove` plus `geometry.dispose()` for zone-owned geometry. **Never dispose the shared materials or textures.** | Disposing a material deletes its program once no other material uses it. Using it again recompiles, which causes a hitch. |
| Memory | Not the binding limit at this art style. One Oakvale is 39 MB of vertex data **(measured)**. It occupies the GPU and, by default, also a JS copy. | The Quest 3 native kill limit is 5.75 GiB PSS (earlier doc). The browser tab's share is undocumented. The risk is leaks. |
| Interiors | Use the same streamer. An interior is a small *cell* tied to a door or mouth. Load it within about 40 m of the door and show it only near or inside. Past a bend in the tunnel, hide the outdoor chunks, switch fog and far plane to interior values, and fade the sun. | `WebGLRenderer` has no occlusion culling, so the app decides what is hidden. The sun casts no shadows, so it would light the tunnel walls. |

**The seam itself can be a line in the data.** It needs no loading strip. Give it a **one-chunk (40 m) height-blend band on each side**, and put it in a pass so the neighbour is mostly hidden by the mountain ring. For Oakvale that is the southern pass: the terrain ends at z = +140 and the road already leaves that way.

## Detailed findings

### 1. What drops a frame in a WebXR session

- The page renders in `XRSession.requestAnimationFrame` callbacks, which run when the session receives a new viewer pose ([WebXR `index.bs` L1128–L1146](https://github.com/immersive-web/webxr/blob/main/index.bs#L1128-L1146)). three.js's `setAnimationLoop` hands the loop to the session while presenting ([r186 `WebGLRenderer.js` L1609–L1619](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1609-L1619)). The frame is presented "immediately after an XR animation frame completes" ([WebXR L2291](https://github.com/immersive-web/webxr/blob/main/index.bs#L2291)). JavaScript tasks on one event loop run one at a time ([HTML: event loop processing model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)). So any main-thread task still running when a pose arrives delays that frame, and so does any extra work inside the callback. That covers a synchronous build, a large upload, a shader link or a GC pause.
- When the page misses, the XR compositor may reproject ([WebXR L970](https://github.com/immersive-web/webxr/blob/main/index.bs#L970)). It runs in a separate thread or process so the page cannot stop it presenting ([L1205](https://github.com/immersive-web/webxr/blob/main/index.bs#L1205)). On Quest this shows as **stale frames**: the compositor re-shows the last frame, and a stale count between 0 and the refresh rate is felt as judder ([Meta: Missed frames and frame recovery](https://developers.meta.com/horizon/documentation/unity/os-missed-frames/), [Meta blog: OVR Metrics + VrApi metrics](https://developers.meta.com/horizon/blog/ovr-metrics-tool-vrapi-what-do-these-metrics-mean/), search extracts). "No dropped frame" in this ticket means **0 stale frames in OVR Metrics while crossing the seam**.
- XR rendering cannot move off the main thread. `navigator.xr`, `XRSystem`, `XRSession` and `XRWebGLLayer` are all `[Exposed=Window]` ([WebXR L270, L280, L631, L2161–L2166](https://github.com/immersive-web/webxr/blob/main/index.bs#L2161-L2166)). So a worker, or an OffscreenCanvas in a worker, can prepare data but cannot draw the XR frame.

### 2. Building geometry off the main thread

**What Oakvale costs today (measured).** I ran `buildForest()`'s geometry steps under Vitest in Node. Glows, water and spinners were skipped because they need a DOM or are small. Three runs:

| Step | Time (ms) |
|---|---|
| `buildLayout()` (heights, roads, plants, structures, colliders) | 201–255 |
| `addTerrain` | 85–116 |
| paths and patches | 4–9 |
| stamping plants, fields, fences and structures into chunks | 96–182 |
| `Chunks.meshes()` → `MeshBuffer.geometry()` (typed arrays and bounding spheres) | 74–255 |

The result is **49 chunks, 790,698 vertices (264k triangles), 39.2 MB** of vertex data. The median chunk is 858 KB and the largest is 2.45 MB (49k vertices, the village chunk). The 24 mountain-ring chunks are 225–413 KB each. Each vertex is 52 bytes: position, normal and colour at 3 floats each, plus `fx` and `uv` at 2 floats each. The geometry is non-indexed ([`src/maps/forest/terrain.ts`](../../../src/maps/forest/terrain.ts), `MeshBuffer.geometry`). The whole build ran **without a DOM**, so the plan and chunk code can run in a worker unchanged. Only `Glows`, the water's ripple texture and `grainTexture` touch `document`, and only when called.

**Workers and transfer.**

- A dedicated worker runs its own event loop. `Worker.postMessage(message, transfer)` takes a transfer list ([HTML source, `Worker` IDL](https://html.spec.whatwg.org/multipage/workers.html#dedicated-workers-and-the-worker-interface)). Transferring an `ArrayBuffer` "is effectively recreating the object while sharing a reference to the underlying data and then detaching the object being transferred" ([HTML: Transferable objects](https://html.spec.whatwg.org/multipage/structured-data.html#transferable-objects), [StructuredSerializeWithTransfer](https://html.spec.whatwg.org/multipage/structured-data.html#structuredserializewithtransfer)). Chunk arrays therefore cross threads without a copy. Anything not in the transfer list, such as plain objects, collider lists or glow positions, is copied by structured clone, which costs time in proportion to its size.
- three.js uses exactly this pattern. `DRACOLoader` posts the compressed buffer to a worker with a transfer list, the worker posts the decoded attribute arrays back with their buffers transferred, and the main thread wraps them in a `BufferGeometry` ([r186 `DRACOLoader.js` L256, L571, L293](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/loaders/DRACOLoader.js#L256)). `KTX2Loader` transcodes textures in a `WorkerPool` ([`KTX2Loader.js` L48, L157](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/loaders/KTX2Loader.js#L48)).
- **A worker's garbage does not pause the render thread.** In Chromium each worker thread owns its own `v8::Isolate` ([Chromium `worker_backing_thread.h` L22, L45](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/workers/worker_backing_thread.h#L22)), and "an isolate is a VM instance with its own heap" ([V8: embedder's guide](https://v8.dev/docs/embed)). V8's major GC still ends with a main-thread pause for marking finalization and compaction ([V8 blog: Trash talk](https://v8.dev/blog/trash-talk)). Today's build allocates heavily: `MeshBuffer` pushes into plain `number[]` arrays, and `Vector3`/`Matrix4` are cloned per plant. That garbage belongs in a worker.
- Vite bundles workers written as `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`, and the options must be static literals ([Vite docs: Web Workers](https://github.com/vitejs/vite/blob/main/docs/guide/features.md#web-workers)). Module workers are in Chrome ([browser-compat-data `api/Worker.json`](https://github.com/mdn/browser-compat-data/blob/main/api/Worker.json), `ecmascript_modules`). Quest's entry mirrors Chrome, so this is medium confidence. The worker bundle includes its own copy of the three.js classes it imports, such as `ModelBuilder`'s `BufferGeometry` and `mergeGeometries`.
- The Quest browser is Chromium-based and tracks recent milestones; a recent release note mentions an update to Chromium M146 ([Meta: Browser release notes](https://developers.meta.com/horizon/release-notes/web/), search extract).

**OffscreenCanvas.**

- `OffscreenCanvas` is exposed in workers, offers `2d`, `webgl` and `webgl2` contexts, and `transferToImageBitmap()` hands out an `ImageBitmap`. `ImageBitmap` is `Transferable` ([HTML: OffscreenCanvas interface](https://html.spec.whatwg.org/multipage/canvas.html#the-offscreencanvas-interface), [ImageBitmap interface](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#the-imagebitmap-interface)). Chrome has had it since 69 ([BCD `api/OffscreenCanvas.json`](https://github.com/mdn/browser-compat-data/blob/main/api/OffscreenCanvas.json); Quest mirrors Chrome).
- Its use here is narrow: painting a large procedural texture in a worker. three.js ignores `flipY` and `premultiplyAlpha` for `ImageBitmap` sources, so those must be set when the bitmap is made ([r186 `WebGLTextures.js` L918–L930](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLTextures.js#L918-L930), [`ImageBitmapLoader.js` L5–L25](https://github.com/mrdoob/three.js/blob/r186/src/loaders/ImageBitmapLoader.js#L5-L25)). Oakvale's textures are three shared canvases of 32×32 or 64×64, made once, so today **OffscreenCanvas is not needed**. A WebGL context in a worker cannot share programs or buffers with the page's context, so it cannot pre-compile or pre-upload for the XR renderer either.

### 3. Time-slicing the work that stays on the main thread

- **Do not schedule streaming work from `window.requestAnimationFrame` or `requestIdleCallback`.** The WebXR spec says an immersive session "MAY affect the rendering opportunity" of the page. On standalone devices, window rAF callbacks "may not be processed while the session is active", and `requestIdleCallback` timing may not line up with the session's frames ([WebXR L1152–L1157](https://github.com/immersive-web/webxr/blob/main/index.bs#L1152-L1157)). Idle periods are defined relative to the *window's* frames and are user-agent defined ([W3C requestIdleCallback](https://w3c.github.io/requestidlecallback/), read from [its source](https://github.com/w3c/requestidlecallback)).
- The only reliable clock is the XR loop itself. Keep a queue and spend a fixed time slice per frame, checked with `performance.now()`. The earlier doc cites Meta's guidance that app logic over about 2 ms per frame needs optimizing. Streaming, gameplay and three.js's own scene traversal share that 13.9 ms.
- Work can run as its own task right after the frame is submitted, instead of lengthening the callback. `scheduler.postTask()` and `scheduler.yield()` are the standard ways to do that ([WICG Prioritized Task Scheduling](https://github.com/WICG/scheduling-apis/blob/main/spec/scheduling-tasks.md)). They are in Chrome 94 and Chrome 129 respectively ([BCD `api/Scheduler.json`](https://github.com/mdn/browser-compat-data/blob/main/api/Scheduler.json); Quest mirrors Chrome). Neither knows when the next XR frame is due, so the time budget still applies. `renderer.compileAsync` already polls with `setTimeout` ([`WebGLRenderer.js` L1549–L1551](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1549-L1551)), which does not depend on window rAF.
- What remains on the main thread per chunk is small if the worker also sends the bounding sphere. That work is creating a `BufferGeometry` and a `Mesh`, setting `geometry.boundingSphere` (so three.js does not loop over the vertices; [`Frustum.js` L146–L166](https://github.com/mrdoob/three.js/blob/r186/src/math/Frustum.js#L146-L166)) and `scene.add`. The zone-level extras, meaning glows, water and spinners, are built once per zone from positions the worker sends.

### 4. Uploading to the GPU without a hitch

**Buffers.**

- three.js uploads a geometry **the first time a mesh using it reaches the render list**. `projectObject` calls `objects.update(object)` only for a visible object that passes the frustum test (or has `frustumCulled = false`) ([`WebGLRenderer.js` L1912–L1916](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1912-L1916)). That uploads **every** attribute in `geometry.attributes`, whether or not the shader reads it ([`WebGLGeometries.js` L65–L77](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLGeometries.js#L65-L77)), through `gl.bufferData` ([`WebGLAttributes.js` L5–L16](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLAttributes.js#L5-L16)). Adding a chunk that is out of view therefore costs nothing until the player turns their head toward it. Then the whole chunk uploads in that frame.
- There is **no public "upload this geometry now" call**. `compile()` only prepares materials ([`WebGLRenderer.js` L1384–L1499](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1384-L1499)), and `initTexture()` exists only for textures ([L3589–L3617](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L3589-L3617)). However, `objects.update` runs *before* the `material.visible` check that decides whether to draw ([L1916 vs L1956](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1956)). So a **staging frame** uploads without drawing: give the new mesh a material with `visible = false` and set `frustumCulled = false` for one frame, then restore the shared material and `frustumCulled = true`. This relies only on public properties, but it depends on render-loop internals, so add a test or comment when r187+ lands.
- **In Chromium an upload is a copy through shared memory, and it can block.** `glBufferData` on the client copies the data into a transfer buffer. If the data does not fit, it is sent in pieces through `BufferSubData` ([Chromium `gles2_implementation.cc` L2190–L2251](https://github.com/chromium/chromium/blob/main/gpu/command_buffer/client/gles2_implementation.cc#L2190-L2251)). Allocating in the ring buffer waits for the GPU process to finish with older blocks ([`ring_buffer.cc` L38–L46, L68–L71](https://github.com/chromium/chromium/blob/main/gpu/command_buffer/client/ring_buffer.cc#L38-L46)). The transfer buffer starts at 64 KB and may grow to 16 MB ([`shared_memory_limits.h` L38–L40](https://github.com/chromium/chromium/blob/main/gpu/command_buffer/client/shared_memory_limits.h#L38-L40)). The GPU process then executes the upload in the same command stream as the frame's draws. The cost therefore scales with bytes and lands both on the main thread and ahead of the frame's rendering. No primary source gives a Quest 3 figure per MB, so it goes on the headset list. (Chromium main as of September 2026; Meta may patch it, so medium confidence for Quest.)
- **Upload fewer bytes.** The chunk material is `flatShading: true` ([`src/models/materials.ts`](../../../src/models/materials.ts)). Under `FLAT_SHADED`, three.js computes normals from screen-space derivatives and never passes the normal attribute on ([`normal_vertex.glsl.js` L2](https://github.com/mrdoob/three.js/blob/r186/src/renderers/shaders/ShaderChunk/normal_vertex.glsl.js#L2), [`normal_fragment_begin.glsl.js` L4](https://github.com/mrdoob/three.js/blob/r186/src/renderers/shaders/ShaderChunk/normal_fragment_begin.glsl.js#L4)). Yet `normal` is uploaded anyway (above). Dropping it saves 12 of 52 bytes per vertex (23%), about 9 MB for Oakvale. Colour and `fx` could also be 8-bit normalized attributes. Verify both visually. `terrain.ts` already notes the normals are ignored.
- **Partial uploads** are possible: `BufferAttribute.addUpdateRange` makes three.js call `bufferSubData` on just that range ([`WebGLAttributes.js` L80–L120](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLAttributes.js#L80-L120)). `BatchedMesh.setGeometryAt` uses it, so chunks could stream into a pre-allocated pool ([`BatchedMesh.js` L714–L791](https://github.com/mrdoob/three.js/blob/r186/src/objects/BatchedMesh.js#L714-L791)). Buffers cannot grow, and resizing is "basically the equivalent to creating a new geometry" ([three.js manual: How to update things](https://github.com/mrdoob/three.js/blob/r186/manual/pages/how-to-update-things.html)).

**Textures.**

- `renderer.initTexture(texture)` uploads ahead of first use, "rather than waiting until first render (which can cause noticeable lags due to decode and GPU upload overhead)" ([`WebGLRenderer.js` L3589–L3617](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L3589-L3617)). three.js allocates with `texStorage2D`, uploads with `texSubImage2D`, and builds mips with `generateMipmap` on the GPU ([`WebGLTextures.js` L1363–L1395](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLTextures.js#L1363-L1395)). MDN recommends that `texStorage` path, and warns that uploads from DOM sources can cause pipeline flushes ([MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices), [source](https://github.com/mdn/content/blob/main/files/en-us/web/api/webgl_api/webgl_best_practices/index.md)).
- For future painted art, Meta recommends KTX2/Basis, which stays compressed in GPU memory ([Meta: WebXR Performance Best Practices](https://developers.meta.com/horizon/documentation/web/webxr-perf-bp/), search extract). `KTX2Loader` transcodes it in workers (above).
- **Project impact:** Oakvale's three textures are shared and made once. A new zone should reuse them. Any zone-owned texture gets an `initTexture` call during staging, one per frame.

**Shaders.**

- A program is chosen by a cache key that includes `fog`, `fogExp2`, `numDirLights`, `numPointLights` and `numHemiLights` ([`WebGLPrograms.js` L315–L317, L341–L346, L472–L481](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLPrograms.js#L472-L481)). `forest.ts` adds its own `HemisphereLight` and `DirectionalLight` to `root`. With two zone roots in the scene those counts go from 1 to 2, every lit material needs a new program, and the lighting doubles. **The lights must move out of `GameMap` into a world-level rig.** The same applies to the sky dome: two domes would overdraw each other.
- Replacing `scene.fog` with a new `Fog` object makes every fogged material re-run `getProgram` ([`WebGLRenderer.js` L2488](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L2488)). That is a cache lookup, not a compile, but it is wasted work. Fog `near`, `far` and `color` are uniforms ([`fog_fragment.glsl.js`](https://github.com/mrdoob/three.js/blob/r186/src/renderers/shaders/ShaderChunk/fog_fragment.glsl.js)), so blending them per frame is free. `walk.ts` creates one `Fog`. Keep one and mutate it.
- `compileAsync(scene, camera, targetScene)` compiles only the materials under `scene`, using `targetScene`'s lights. The lights must already be as they will be when rendered ([`WebGLRenderer.js` L1384–L1394, L1515–L1573](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1515-L1573)). So call `renderer.compileAsync(zoneRoot, camera, scene)` before adding a zone root. It polls `COMPLETION_STATUS_KHR`, which does not block ([Khronos `KHR_parallel_shader_compile`](https://github.com/KhronosGroup/WebGL/blob/main/extensions/KHR_parallel_shader_compile/extension.xml); in Chrome since 76 per [BCD](https://github.com/mdn/browser-compat-data/blob/main/api/KHR_parallel_shader_compile.json)). Without the extension, three.js marks programs ready immediately and "it may cause a stall when it's first used" ([`WebGLProgram.js` L992–L1007](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLProgram.js#L992-L1007)).
- On first use of a program, three.js reads info logs and `LINK_STATUS` when `renderer.debug.checkShaderErrors` is true, which is the default ([`WebGLProgram.js` L863–L956](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLProgram.js#L863-L956), [`WebGLRenderer.js` L164–L182](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L164-L182)). MDN lists those calls as round-trips that can stall, "as long as 1ms" or longer ([MDN: Avoid blocking API calls](https://github.com/mdn/content/blob/main/files/en-us/web/api/webgl_api/webgl_best_practices/index.md)). Set it to `false` in production builds.
- **Project impact:** with one light rig, one `Fog` and shared materials, a new zone creates **zero** programs. Precompile every material any zone uses once, at startup, including water and glows. Assert in a `?perf` build that `renderer.info.programs.length` does not change during streaming ([`WebGLRenderer.js` L484](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L484)).

### 5. Unloading, and memory in the Quest browser

- Removing a mesh frees nothing on the GPU. Buffers are deleted only by `BufferGeometry.dispose()`. Programs are deleted only when every material using them is disposed. Textures are freed only by `Texture.dispose()`. `ImageBitmap` sources also need `close()` ([three.js manual: How to dispose of objects](https://github.com/mrdoob/three.js/blob/r186/manual/pages/how-to-dispose-of-objects.html)). `dispose()` deletes each attribute's buffer and decrements `renderer.info.memory.geometries` ([`WebGLGeometries.js` L8–L49](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLGeometries.js#L8-L49)).
- **Unloading a chunk** means `remove` plus `geometry.dispose()`, and dropping the JS references so the arrays can be collected. **Never dispose `sharedModelMaterial()`, the water or glow materials, or the shared textures.** The manual says reusing a disposed material recompiles its program, and "the worst thing that can happen is performance drop for a single frame". That drop is exactly the hitch this ticket is avoiding.
- three.js keeps each attribute's typed array after upload, so a loaded chunk costs its bytes twice: once on the GPU and once in the JS heap. `attribute.onUpload(cb)` runs after the upload "to perform clean-up operations … when attribute data are not needed anymore on the CPU side" ([`BufferAttribute.js` L632–L646](https://github.com/mrdoob/three.js/blob/r186/src/core/BufferAttribute.js#L632-L646)). Nulling the array there halves the footprint, but it has costs. The bounding sphere must come from the worker. Raycasts against the chunk stop working (the game uses `heightAt`, not raycasts). After a WebGL context loss the chunk must be rebuilt from the worker. A streamer can do that rebuild anyway.
- **Quest limits.** The earlier doc found that Quest 3 kills native apps at 5.75 GiB PSS and that the browser tab's share is undocumented (Meta search extracts). Nothing better was found for the tab. On this art style one fully loaded Oakvale is 39 MB of vertex data, or about 80 MB with the JS copy. The worker's transient `number[]` arrays add a peak (8 bytes per number) that is freed with the worker's heap. Even three zones loaded stay in the low hundreds of MB, so **memory is not the binding constraint; leaks are**.
- **Measuring.** `renderer.info.memory.{geometries,textures}` counts GPU objects ([`WebGLInfo.js`](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgl/WebGLInfo.js)). `performance.measureUserAgentSpecificMemory()` needs a secure, cross-origin-isolated page ([MDN source](https://github.com/mdn/content/blob/main/files/en-us/web/api/performance/measureuseragentspecificmemory/index.md)), which the static GitHub Pages site probably is not. Chromium's non-standard `performance.memory` ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/Performance.json), marked deprecated) and heap snapshots over `chrome://inspect` are the practical tools.

### 6. Draw calls and triangles with two zones in view

- **Merging is already done per chunk.** Oakvale stamps ground, plants, fields, fences and buildings into one mesh per 40 m chunk with the shared material, so a visible chunk is 1 draw per eye ([`src/maps/forest/forest.ts`](../../../src/maps/forest/forest.ts)). Culling tests each chunk's bounding sphere against the frustum ([`Frustum.js` L146–L166](https://github.com/mrdoob/three.js/blob/r186/src/math/Frustum.js#L146-L166)). In XR that test runs once per frame, against a union frustum covering both eyes ([`WebXRManager.js` L648–L709](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webxr/WebXRManager.js#L648-L709), [`WebGLRenderer.js` L1686–L1709](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1686-L1709)). Drawing still happens once per eye (earlier doc).
- **Measured estimate from the per-chunk vertex counts.** This uses a 110° horizontal union frustum and 240 m far plane, and counts chunks by bounding sphere:

  | Where | Chunks in view | Triangles per eye (Oakvale only) |
  |---|---|---|
  | Village, facing north | 24 | ~123k |
  | Village, facing south | 24 | ~152k |
  | South edge of the play area (z = 70), facing the pass | 13 | ~64k |
  | Mine front, facing north | 13 | ~54k |

  Draw calls at the seam are fine. Take ~40 chunks from both zones plus a few per-zone meshes (water, glows, spinners), and the total is about 100 XR draw calls before enemies, weapons and HUD. That leaves room within the 300 budget. **Triangles are the tighter limit.** The village view is already at 250–300k over both eyes, which is the earlier doc's rule of thumb. Distance-based detail (below) fixes both. The 110° FOV is Meta's published figure from secondary pages ([VRcompare](https://vr-compare.com/headset/metaquest3)); log the real projection on the headset.
- **LOD.** three.js `LOD` switches levels by camera distance and takes a `hysteresis` fraction to stop flicker ([`LOD.js` L113–L116](https://github.com/mrdoob/three.js/blob/r186/src/objects/LOD.js#L113-L116); updated per frame in `projectObject`, [`WebGLRenderer.js` L1872–L1874](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1872-L1874)). A level that was never shown was never uploaded, so it needs the same staging frame. A chunk streamer that owns "full / proxy / unloaded" per chunk does the same job and also controls memory. The forest already has a cheap tree set for far chunks (`plantPrototypes(true)`), so the proxy has a starting point. A proxy made of 8 m ground cells and far trees is about 1/16 of a chunk's ground triangles.
- **`BatchedMesh`** can draw many chunks in one call with per-object frustum culling and `setVisibleAt` ([`BatchedMesh.js` L205–L221, L1163](https://github.com/mrdoob/three.js/blob/r186/src/objects/BatchedMesh.js#L205-L221)). Without `WEBGL_multi_draw` it loops one draw per object ([`WebGLRenderer.js` L1315–L1335](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js#L1315-L1335)). The extension is in Chrome 86 ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/WEBGL_multi_draw.json)); check it on the headset. It also needs a `batching` variant of the model shader. It is not needed at about 40 chunk draws. Keep it in reserve for proxies if draw calls ever bind.
- **No occlusion culling in `WebGLRenderer`.** Occlusion queries exist only in the `WebGPURenderer` path (`src/renderers/common/RenderList.js` and the WebGPU and WebGL-fallback backends in r186). Grep finds none in `WebGLRenderer`. Chunks of the next zone behind Oakvale's mountain ring are drawn if they are in the frustum and within the far plane. Only the app can hide them.
- **Fog and far plane are planar.** three.js fog uses view depth, `vFogDepth = -mvPosition.z` ([`fog_vertex.glsl.js`](https://github.com/mrdoob/three.js/blob/r186/src/renderers/shaders/ShaderChunk/fog_vertex.glsl.js)), and the far plane is a depth too. An object at angle θ off the view axis is fogged as if it were `cos θ` times as far. At the edge of a 110° view, a hill 240 m away is fogged like one 138 m away, and it reappears or vanishes as the head turns. For streaming this means that anything within `far / cos(θ_edge)` can be drawn, about 420 m. Making fog radial (`length(mvPosition.xyz)`) fixes the look. Override `ShaderChunk.fog_vertex` at startup, before any program compiles, or patch it in the model material's existing `onBeforeCompile`. Then cull chunks beyond `fog.far` plus the chunk radius in the streamer, and the loaded area stays a disc of about 230 m.
- `camera.far` flows into the session's `depthFar` through `updateRenderState` and "won't apply until the next frame" ([`WebXRManager.js` L736–L765](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webxr/WebXRManager.js#L736-L765)). Changing the far plane per zone or per interior is cheap, but it lags by one frame.

### 7. Streaming an interior (the mine, a building)

- The mechanism is the same streamer. An interior is a **cell**: a few meshes (a mine of a tunnel and some chambers is on the order of one or two chunks' worth of vertices), its colliders and floor heights, point-light positions for the pool, and an interior atmosphere (fog, far plane, light intensities). It is keyed to a door or mouth. Load and stage it when the player comes within about 40 m of the door, a few frames of uploads.
- **Visibility is app logic** (no occlusion culling, above). Hide the interior while the player is outside and away from the door. Once the player is inside and past a bend in the tunnel, hide the outdoor chunks. That removes the 13 chunks (26 XR draw calls, ~54k triangles per eye) seen from the mine front. At the same point, blend fog `near`/`far`/`color` and `camera.far` to interior values; the earlier doc's dungeon setting is fog and far plane at 15–25 m. The bend means the player never sees the outdoors switch off.
- **Light count stays constant.** The 4-point-light pool moves to the nearest interior torches, as the earlier doc prescribes. The sun and hemisphere stay in the scene, since removing them would change the program key, but their `intensity` fades to near zero inside. That is needed because there are no shadow maps: a directional light lights every surface that faces it, tunnel walls included ([earlier doc §4](../../../docs/quest-3-browser-performance-budget.md)). An alternative is a baked per-vertex "sky visibility" factor for the sun, which would let the mouth area look right in daylight.
- **Walking in.** Inside the interior's footprint, `heightAt` and `resolve` must come from the cell, not the terrain. The terrain above a tunnel faces up, and the model material is single-sided (no `side` is set in [`materials.ts`](../../../src/models/materials.ts), so the default `FrontSide` applies). So the hillside is culled when seen from inside. At the mouth, though, the chunk builder must skip the ground triangles where the tunnel cuts into the hillside.
- **Small buildings** (the inn, houses) can skip streaming. Build the interior with the chunk as a separate mesh, keep it hidden, stage its upload when the player approaches, and show it at the door. It costs 1 extra draw only while visible.

## How this constrains the project

**Seam width and timing (rule of thumb, from the numbers above).**

- *Player speed:* 2.2 m/s on the stick (`CONFIG.player.moveSpeed`), and 6.6 m/s with the desktop Shift boost in walk mode. Design for up to 7 m/s in case a sprint is added (map: "Getting around").
- *Chunk latency is small.* At 7 m/s the player crosses one 40 m chunk row in about 6 s, and each row brings about 7 new chunks into the full-detail radius. Even if the Quest builds 10× slower than desktop (about 1.5–5 ms per chunk's `geometry()` plus its share of stamping, **measured** on desktop), the worker keeps up. One upload per frame is 7 frames. **Prefetch one chunk (40 m) beyond each radius and unload one chunk beyond that.** That is the hysteresis.
- *Zone-plan latency is the long pole.* `buildLayout()` is about 0.2–0.25 s on desktop **(measured)** and must finish before any chunk of that zone can be built. The next zone must have proxies in place before anything of it is within the draw radius: about 230 m with radial fog, up to about 420 m without. Oakvale is 280 m across, and its play area reaches 224 m from the southern border. So in practice: **when a zone becomes current, load all its neighbours' plans, and their proxies in view.** The plan is small: a 141×141 height grid is 80 KB, plus collider and plant lists.
- *The seam is a line with a 40 m blend band on each side.* Both zones' height functions must agree exactly along the border, so blend each zone's terrain to a shared border profile across the last chunk. Put the border across Oakvale's southern pass at z = +140. That line lies on the existing 40 m chunk grid (`FOREST.half` = 140), and the mountain ring hides the neighbour everywhere except down the pass. Place the second zone's origin on the same grid so chunk keys are global.
- *Walkable bounds* are clamped to Oakvale's play square today (`Colliders` bounds, `GameMap.bounds` = ±84). The pass from z = 84 to 140 must become walkable, and a crossing needs both zones' bounds and colliders queried within about 1 m of the border.

**What the player sees across it.**

- From inside Oakvale, the second zone shows only down the southern pass: full detail within about 120 m, proxies beyond, all under the current zone's fog. From 120 m, fog is about half strength with today's `near` = 45 and `far` = 200, so the proxy-to-full swap happens in haze. Tune the radius on the headset against visible popping.
- While crossing the 40 m band, fog `near`/`far`/`color`, background, sky colours and sun and hemisphere colours lerp from Oakvale's values to the second zone's by the player's position. These are all uniforms, so nothing recompiles. There is no line, no pause and no text. A road sign or a change in trees is a design choice for ticket 10, not a technical need.
- The sky is one world-level dome. What is culled at the far edge must already be fog-coloured against a fog-coloured background, or a silhouette pops. Today's dome is haze-coloured only in its lowest ~1° (`e < 0.02` in [`sky.ts`](../../../src/maps/forest/sky.ts)). Widen that band to cover distant ridges, or keep the far cull beyond where ridges stand out.

**Changes `src/maps/` would need.**

1. **Lights, sky, fog and far plane move out of the zone into a world.** Add a `World`, for example `src/maps/world.ts`, that owns the fixed light rig (1 hemisphere, 1 directional, 4 pooled points), one sky, one `Fog`, `camera.far`, and the streamer. A zone contributes an *atmosphere* (colours, fog near and far, light colours and intensities) that the world blends. `GameMap.root` stops carrying lights and `buildSky`.
2. **Split a zone into a plan and chunks, both pure and DOM-free, runnable in the worker and in Vitest.** Sketch:
   ```ts
   interface ZoneInfo {                       // replaces MapInfo for streamed zones
     id: string; label: string;
     origin: { x: number; z: number };        // on the 40 m chunk grid, world metres
     neighbours: readonly string[];
     plan(): ZonePlan;                         // today's buildLayout(): heights, colliders, spawn, landmarks, atmosphere
     chunk(plan: ZonePlan, key: ChunkKey, detail: 'full' | 'proxy'): ChunkData;
   }
   interface ChunkData {                       // everything transferable
     key: ChunkKey; detail: 'full' | 'proxy';
     attributes: Record<string, Float32Array | Uint8Array>;
     sphere: { x: number; y: number; z: number; r: number };
     glows: Float32Array;                      // positions for the zone's glow billboards
   }
   ```
   `addTerrain` and the stamping loops become per-chunk: filter plants and structures by chunk, and build only that chunk's ground cells. The worker (`src/maps/stream.worker.ts`) holds plans and answers "build chunk K at detail D", nearest first, posting results with `postMessage(data, buffers)`.
3. **The main thread holds only what it needs every frame.** That is a `ZoneRuntime` per loaded zone, with `heightAt` rebuilt from the transferred height grid plus decks, `resolve` from the collider lists, and `update()` for glows, water and spinners. The `World` dispatches `heightAt`, `resolve` and `update` by position. `walk.ts` talks to the `World`, not to one `GameMap`.
4. **A streamer with a per-frame budget.** Each frame it works out which chunks should be full, proxy or unloaded from the player position (a pure function, unit-testable). It stages at most one upload per frame (hidden material, `frustumCulled = false` for one frame), swaps visibility, and disposes what falls out. It calls `compileAsync(zoneRoot, camera, scene)` before a zone's first chunk shows.
5. **Registry.** `registry.ts` keeps `import.meta.glob`. A zone also needs a world placement (`origin`) and adjacency (`neighbours`). The worker needs the same zone list, so check that Vite applies `import.meta.glob` inside the worker bundle. The small `crypt` map and interiors can stay whole-build `GameMap`s hosted by the world as a single cell.
6. **Tests and tooling.** Add tests that border heights of adjacent zones match, that chunk builds are deterministic, and that the streamer's decisions are right at sample positions. Add a `?perf` HUD line for loaded chunks, bytes uploaded this frame and `renderer.info.programs.length`. Set `renderer.debug.checkShaderErrors = false` in production.
7. **Byte diet** (optional, measure first): drop the unused `normal` attribute, and make `color` and `fx` 8-bit normalized. That roughly halves upload and memory per chunk.
